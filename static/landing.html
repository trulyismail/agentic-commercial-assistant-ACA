01 — How it works

Balance agent
control with agency.

A state graph, not a prompt chain. A supervisor dynamically routes four specialised agents, and the graph knows how to interrupt itself — then resume exactly where it stopped, even after a restart.

START attachments classifier CRM memory risk scan extractor supervisor strategist ⏸ HUMAN PAUSE CRM write END
01

Human-in-the-loop

Easy-to-add moderation and quality controls prevent the agent veering off course. Here it is structural, not conventional.

02

Durable execution

The graph survives pauses, restarts and process handoffs. An interrupted analysis resumes where it stopped, not from the beginning.

03

Persistent memory

Short term: shared graph state. Long term: the CRM and knowledge base, read before processing — returning customers and duplicates caught on arrival.

04

First-class streaming

Every node reports as it works: you watch the reasoning unfold rather than a spinner turning.

The handbrake

The CRM write node is compiled behind interrupt_before=["action"]. The graph cannot reach it without an explicit human resume. The rule therefore holds on every surface at once — UI, API, Slack, n8n — because it lives in the graph, not in the button.

02 — Since v1

Six shipped passes,
every one tested.

The first version could read an email and draft a reply. It can now be operated by a team: several people, under a client's own brand, with a record of who did what and a report to send at month end.

§17 — White label

Appearance becomes data

22 tokens (name, logo, 10 colours, font, radius, density, light/dark, animation level) resolved at runtime, 18 sector presets. Shipping in a client's colours no longer means modifying the product.

§17 — Activity journal

Who did what, from which machine

25 hash-chained actions with normalised IP, declared user agent, workstation fingerprint and unusual-device detection. Failed logins included: a brute-force lock that blocks silently teaches you nothing.

§18 — Second factor

TOTP on admin accounts

RFC 6238, standard library only, checked against the official test vectors, with a scannable enrolment QR. Scoped to admin: imposing it on an operator would be repaid in workarounds.

§18 — Lead history

Timeline and draft diff

What happened on this lead, in order, and what the human actually changed before sending. The data had always been recorded; only the view was missing.

§19 — Scheduling

"Send Monday, 9am"

What gets scheduled is the Gmail draft you already reviewed — edit or delete it in Gmail before the deadline and your version wins. The human authorisation exists; it is simply prior to execution.

§19 — Intake window

No more 3am analyses

Days, hours and frequency set from the UI and re-read every cycle without a restart. Handles the overnight window, which a naive comparison silently turns into an empty range.

§20 — Peer review

"I'm not deciding this alone"

An operator hands several emails to an admin in one gesture, with a note and a priority. That third gesture — neither approve nor reject — existed nowhere in the data model.

§20 — Reporting

The month, against the last one

The automatic monthly PDF and the custom report share one engine. Every KPI declares which direction is favourable: a rising response time is a degradation, not growth.

§21 · §22 — Design

Measured on the rendered page

Five written rules had never rendered — invisible to review, since dead CSS raises no error. The dashboard now shows a change, not just a state.

03 — Security & compliance

Built to be trusted
with a real
inbox.

A sales assistant sees confidential RFPs, prospect contact details and your own price list. The controls opposite are not a deployment option — they are the condition for plugging this into anything other than a demo mailbox.

Twelve controls, in five groups. Open the one that concerns you — all of them are here, including in print.

ACA_ENV=production → refuses to boot unguarded
01Human validation cannot be bypassed. Guaranteed by how the graph is compiled, not by a button — so it holds on all four surfaces at once.
02Two hash-chained journals. Each row seals the previous one: editing or deleting an entry breaks the chain, and verification locates the break. Tamper-evident, not tamper-proof — stated without exaggeration.
03Named accounts, three roles. Per-user salted PBKDF2-HMAC-SHA256, cost stored inside the hash, constant-time compare and a dummy hash on unknown accounts — response time cannot enumerate valid usernames.
04TOTP second factor on admins. An account that can create other admins, reroute sales alerts and decide what the AI asserts to prospects no longer rests on one factor.
05Progressive lockout, bounded sessions. Exponential backoff after 5 failures, an 8h absolute TTL and a 30min idle timeout, strictest bound winning. Activity never extends the absolute TTL.
06Prompt injection flagged. Deterministic bilingual detection, never blocking: it makes the human gate informed. An instruction buried on page 14 of an RFP no longer reads as one more plausible sentence.
07Contractual red flags detected. Unlimited liability, late penalties, non-compete, bank guarantee — the drafting agent then refuses to commit and defers to legal.
08GDPR end to end. Age-based purge, immediate right-to-erasure for one person across all four places their data actually lives, and two-speed retention — sensitive events outlive routine usage noise.
09Signed monthly archives. A CSV export of the journal plus its SHA-256 digest, never overwritten: a retention purge cannot silently replace a complete archive with a truncated one.
10Bounded API. Constant-time shared key, sliding-window rate limit, payloads rejected before decoding and before the LLM, a settings whitelist, and /docs closed in production.
11HMAC signing in both directions. Slack clicks are verified and fail closed if the secret is missing; outbound webhooks are signed with the timestamp folded into the signature, against replay.
12Tenant isolation in the database. Postgres Row-Level Security via a session variable, verified under a restricted application role — FORCE RLS does not constrain a role holding BYPASSRLS, which would make an all-green report meaningless.

The Integration Ecosystem

Every connection is optional. A missing variable means "feature skipped", never a crash — the bare minimum is one Groq key and one Google Sheet.

What is verified live —

Verified against the real services

✓Gmail — read, label, in-thread drafts, forwards
✓Google Sheets — CRM, knowledge base, enrichment cache
✓Groq · Gemini · Tavily — classification, embeddings, web research
✓HubSpot — contact, deal, note and associations, then cleaned up
✓Supabase — pgvector, shared checkpointer, RLS under a restricted role
✓Slack — alerts and support / HR routing
✓GDPR — age-based purge and right to erasure
✓Three-role walkthrough — admin (through TOTP enrolment), operator, viewer

Coded and tested, never exercised for real

○The n8n workflow — no instance exists for this project
○Stripe billing — no test account
○Slack approval buttons — need a Slack app and a public URL
○Scheduled send — never fired against a real Gmail account
○The monthly report — never run over twelve months of real data
○The Docker image — Docker is not installed here; only the compose profiles are validated
○TLS and hosting — the runbook is written, nothing is hosted
○Mobile — checked on a resized browser, not on a real device

Every one of these is a missing account, device or host — not a missing piece of code.
