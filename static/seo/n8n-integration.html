ACA + n8n — the orchestrator doesn't replace the judgement

A common misconception, stated plainly because it shapes how this integration should be evaluated: n8n does not make ACA automatic — ACA is already autonomous up to the validation pause, on its own, via a background poller and a scheduler. What n8n adds is wiring: connecting ACA's events to whatever else a team already runs, without reimplementing ACA's reasoning inside a workflow canvas.

How it works

  1. Five signed outbound events (analysis.paused, analysis.clarification, analysis.routed, lead.validated, lead.rejected) — an n8n workflow becomes event-driven instead of polling on a Schedule node.
  2. Attachments accepted directly over the API (base64, bounded at 10 files / 20 MB decoded), so a multi-document RFP reaches the same graph n8n triggers as it does through the manual UI.
  3. A known thread_id returns the existing analysis with already_exists: true — n8n's default HTTP-node retry behaviour cannot trigger a duplicate two-70B-model analysis and a duplicate team notification.
  4. GET /health makes no external call and leaks no secret — an orchestrator can probe it every few seconds without burning API quota.
Every mechanism above is covered by automated tests (attachment bounds rejected before the LLM is ever called, idempotence, the async mode, each webhook firing at the correct moment). Not exercised against a real n8n instance or workflow — none exists for this project; n8n would simply be an HTTP client and webhook subscriber of this API.
