Intégration

ACA + n8n — l'orchestrateur ne remplace pas le jugement

Une confusion fréquente, dite ici clairement car elle détermine comment évaluer cette intégration : n8n ne rend pas ACA automatique — ACA est déjà autonome jusqu'à la pause de validation, seul, via un scrutateur en arrière-plan et un planificateur. Ce que n8n ajoute, c'est le câblage : relier les événements d'ACA à tout ce qu'une équipe utilise déjà, sans réimplémenter le raisonnement d'ACA dans un canevas de workflow.

Comment ça marche

  1. Cinq événements sortants signés (analysis.paused, analysis.clarification, analysis.routed, lead.validated, lead.rejected) — un workflow n8n devient piloté par événement plutôt qu'en sondage via un nœud Schedule.
  2. Les pièces jointes sont acceptées directement via l'API (base64, plafonnées à 10 fichiers / 20 Mo décodés), pour qu'un appel d'offres multi-documents atteigne le même graphe que n8n déclenche que via l'interface manuelle.
  3. Un thread_id déjà connu renvoie l'analyse existante avec already_exists: true — le comportement de reprise par défaut du nœud HTTP de n8n ne peut donc pas déclencher une analyse en double (deux appels à un modèle 70B) ni une notification en double à l'équipe.
  4. GET /health n'effectue aucun appel externe et ne révèle aucun secret — un orchestrateur peut le sonder toutes les quelques secondes sans consommer de quota d'API.
Chaque mécanisme ci-dessus est couvert par des tests automatisés (limites des pièces jointes rejetées avant même l'appel au LLM, idempotence, mode asynchrone, chaque webhook déclenché au bon moment). Non testé contre une vraie instance ou un vrai workflow n8n — aucun n'existe pour ce projet ; n8n serait simplement un client HTTP et un abonné aux webhooks de cette API.
