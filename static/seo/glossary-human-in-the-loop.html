What is human-in-the-loop AI?

Human-in-the-loop (HITL) describes an AI system architected so that a person's approval is a required step before a consequential action — not an optional review someone could skip, but a point the system genuinely cannot pass without a person acting.

The distinction that matters in practice is between a system that can be checked and one that must be checked. Many products describe themselves as human-in-the-loop because a person could review the output before it's used elsewhere. That is oversight, not a loop — nothing stops the system from proceeding if nobody looks.

A concrete example, from this project: ACA's graph is built with LangGraph's interrupt_before=["action"], which is a structural property of the compiled graph, not a check somewhere in application code. The graph physically cannot reach its CRM-writing step without a person resuming it. In demo mode, a separate guard_write() function goes further and raises an exception rather than silently skipping the write — because for a safety mechanism, "absent = skipped" is the wrong default; a silent no-op there would be exactly what a human-in-the-loop system must never do.

A second, subtler form appears mid-process rather than at the end: ACA also pauses to ask a clarifying question when a lead's stated need is too ambiguous to act on (a dynamic interrupt(), resumed with the human's answer). Human-in-the-loop is not only the final gate — it can be any point where the system's confidence genuinely runs out.

Both mechanisms described are exercised by the project's automated test suite (interrupt-before-action, the demo-mode guard raising, and the dynamic clarification interrupt resuming correctly).
