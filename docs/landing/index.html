Assistant Commercial Agentique · prototype de stage

Le travail est déjà fait quand vous ouvrez votre boîte mail.

ACA lit les e-mails commerciaux entrants et leurs pièces jointes, qualifie le lead, interroge votre base de connaissances, enrichit le profil de l'entreprise, rédige la réponse — puis s'arrête.

À votre connexion, il ne reste qu'à relire et cliquer « Valider ». Aucune ligne n'entre dans le CRM, aucun e-mail ne part avant ce clic. C'est un rédacteur, pas un agent lâché sur votre CRM.

Le problème

Un cahier des charges de 40 pages arrive un vendredi à 18 h.

Le prospect attend une réponse lundi. Entre-temps il faut lire le document, retrouver vos tarifs, vérifier qui est ce client, savoir si on lui a déjà parlé, et rédiger quelque chose de présentable. Le goulot d'étranglement n'est pas la décision commerciale — elle prend deux minutes. C'est tout ce qu'il faut rassembler avant de pouvoir la prendre.

1

Le tri manuel coûte cher

Chaque e-mail est ouvert, lu et classé à la main — y compris les spams, les candidatures et les tickets de support, qui n'ont rien à faire dans un pipeline commercial.

2

Le contexte est éparpillé

Les tarifs sont dans un tableur, l'historique dans le CRM, le profil du prospect sur le web. Personne ne consolide les trois avant de répondre.

3

Automatiser fait peur — à raison

Un agent qui écrit tout seul dans le CRM et envoie des e-mails à de vrais prospects, c'est un incident qui attend son heure.

Comment ça marche

Une équipe d'agents, un superviseur, et un frein à main.

Un graphe d'états LangGraph, pas une chaîne de prompts. Un superviseur oriente dynamiquement quatre agents spécialisés, et le graphe sait s'interrompre — puis reprendre exactement là où il s'était arrêté, même après un redémarrage.

START→ Ingestion PJ→ Classifieur→ Mémoire CRM→ Scan de risques→ Extracteur→ Clarification ❓→ Superviseur
EnrichissementProfil de l'entreprise depuis le domaine de l'expéditeur, mis en cache.
ConnaissanceRAG hybride dense + mots-clés sur votre FAQ, fusion RRF.
VeilleRepli web quand la FAQ ne sait pas — et elle s'enrichit au passage.
Stratège → RéflexionRédige la proposition, puis se relit et se corrige une fois.
Superviseur— FINISH → Routage→ Notification→ ⏸️ PAUSE→ Action : écriture CRM→ END
⏸️

Le frein à main est structurel, pas conventionnel. Le nœud d'écriture est compilé derrière interrupt_before=["action"] : le graphe ne peut pas l'atteindre sans reprise explicite. La règle tient donc sur toutes les surfaces — interface, API, Slack, n8n — parce qu'elle est dans le graphe, pas dans le bouton.

Deuxième pause, plus rare : quand le besoin du prospect est ambigu, le graphe pose une question plutôt que d'inventer une réponse, et attend.

Ce qui distingue le projet

Trois partis pris techniques.

01

Multimodal dès l'entrée

PDF, Word et Excel joints sont extraits et analysés avec le corps du message — un appel d'offres arrive rarement en texte brut. Le texte combiné est plafonné une seule fois, pour que dix pièces jointes ne fassent pas exploser le contexte.

02

RAG « sans base de données »

La base de connaissances vit dans un Google Sheets que vos commerciaux éditent eux-mêmes. Recherche hybride : embeddings sémantiques et correspondance exacte, fusionnées par RRF — parce qu'une référence produit ou un SLA « 99,9 % » échappe aux embeddings seuls. pgvector prend le relais si le volume l'exige.

03

Mémoire hybride

Court terme : le checkpointer LangGraph, qui survit aux pauses, aux redémarrages et au passage d'un processus à l'autre. Long terme : le CRM et la FAQ, relus avant traitement — client récurrent et doublon détectés d'entrée.

Vérifié contre les vrais services

  • Gmail — lecture, marquage, brouillons en fil
  • Google Sheets — CRM, FAQ et cache d'enrichissement
  • Groq · Gemini · Tavily — classification, embeddings, veille
  • HubSpot — contact, deal et note créés, puis supprimés
  • Supabase — pgvector, checkpointer partagé, RLS multi-tenant
  • Slack — alertes et routage support/RH
  • RGPD — purge par ancienneté et droit à l'effacement

Codé et testé, jamais exercé en réel

  • Le workflow n8n — aucune instance n8n n'existe pour ce projet
  • La facturation Stripe — aucun compte de test
  • Les boutons d'approbation Slack — demandent une app Slack et une URL publique
  • TLS — la procédure est écrite, rien n'est hébergé

Chacun de ces quatre points est un compte ou un hébergement manquant, pas une pièce de code absente.

Sécurité & conformité

Conçu pour qu'on puisse le brancher sur une vraie boîte mail.

Validation humaine non contournable

Garantie par la compilation du graphe, pas par un bouton — donc vraie sur les quatre surfaces à la fois.

Journal d'audit chaîné

Chaque ligne scelle la précédente : modifier ou supprimer une entrée casse la chaîne, et la vérification localise la rupture. Tamper-evident, dit sans exagérer.

Comptes nominatifs et rôles

Mots de passe PBKDF2 salés, rôles admin/operator, verrou progressif, sessions à TTL absolu et à inactivité.

RGPD de bout en bout

Purge par ancienneté et droit à l'effacement immédiat d'une personne, sur les quatre emplacements où ses données vivent réellement.

Injections de prompt signalées

Détection déterministe, jamais bloquante : elle rend le gate humain informé. Une consigne cachée page 14 d'un cahier des charges ne passe plus pour une phrase de plus.

Le mode production ferme les portes

ACA_ENV=production renverse le défaut : l'application refuse de démarrer s'il manque une protection, au lieu de la sauter en silence.

Essayer

Sans compte, sans clé, sans configuration.

Le mode démonstration exécute le vrai graphe — mêmes agents, même superviseur, même auto-critique, même pause de validation — avec un modèle simulé. Les écritures CRM y sont matériellement bloquées : une démonstration qui pollue un vrai CRM serait pire que pas de démonstration. 

# Le graphe complet sur 6 e-mails de démonstration, zéro clé d'API
python -m aca.core.app

# Ou l'interface, en mode démonstration
ACA_DEMO_MODE=1 streamlit run ui.py

En conditions réelles, le strict minimum est une clé Groq et un Google Sheets. Tout le reste est optionnel — une variable absente signifie « fonctionnalité ignorée », jamais un plantage.

pip install -r requirements.txt
cp .env.example .env              # puis GROQ_API_KEY + GOOGLE_SHEETS_ID
python scripts/run_solo.py        # API + interface + poller + planificateur

Interface sur localhost:8501, API sur localhost:8000 (sonde : /health). Les 54 variables d'environnement sont documentées une par une dans .env.example.
